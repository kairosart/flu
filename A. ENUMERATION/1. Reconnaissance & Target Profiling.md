Reconnaissance began with host discovery and a full TCP port scan of the target to build a complete picture of the exposed attack surface before any service-specific probing.

## Host Discovery

First step is always to confirm the target is alive and identify the OS via the TTL. An ICMP echo with a TTL of `61` is a strong indicator of a **Linux** host (Windows defaults closer to `128`).

```bash
ping -c 2 192.168.173.41
```

```
64 bytes from 192.168.173.41: icmp_seq=1 ttl=61 time=44.0 ms
64 bytes from 192.168.173.41: icmp_seq=2 ttl=61 time=44.2 ms
```

- **Host is up**, average RTT ~44 ms, `ttl=61` → **Linux**.

## Full TCP Port Scan

To avoid missing services on non-standard ports, scan **all 65,535 TCP ports** with a raised rate before running version detection.

```bash
nmap -Pn -p- -T4 --min-rate 1500 192.168.173.41
```

```
PORT     STATE SERVICE
22/tcp   open  ssh
8090/tcp open  opsmessaging
8091/tcp open  jamlink
```

Only three TCP ports are exposed:

| Port | State | Nmap guess |
|------|-------|------------|
| 22/tcp | open | ssh |
| 8090/tcp | open | opsmessaging |
| 8091/tcp | open | jamlink |

## Service & Version Detection

With the open ports known, run version detection, default scripts and OS fingerprinting on just those ports (faster and less noisy than against all ports).

```bash
nmap -Pn -sV -sC -O --reason -p 22,8090,8091 192.168.173.41
```

```
PORT     STATE SERVICE       VERSION
22/tcp   open  ssh           OpenSSH 9.0p1 Ubuntu 1ubuntu8.5 (Ubuntu Linux; protocol 2.0)
8090/tcp open  opsmessaging? syn-ack ttl 61
8091/tcp open  jamlink?      syn-ack ttl 61
```

### Breakdown of the Flags

- `-Pn`: Skip host discovery and treat the target as online (useful when ICMP is filtered).
- `-p-`: Scan all 65,535 TCP ports instead of Nmap's default top 1,000.
- `-sV`: Probe open ports to determine service/version information.
- `-sC`: Run the default set of NSE (Nmap Scripting Engine) scripts.
- `-O`: Enable OS detection.
- `--reason`: Explain why each port received its state (e.g. `syn-ack`).
- `-T4`: Aggressive timing template for speed.

### Findings

- **22/tcp** → `OpenSSH 9.0p1 Ubuntu 1ubuntu8.5` → confirms an **Ubuntu Linux** host.
- **8090/tcp** → version undetermined by Nmap; flagged for manual web enumeration.
- **8091/tcp** → version undetermined by Nmap; flagged for manual web enumeration.
- **OS:** Linux (kernel); the OS fingerprint was reported as incomplete because the host did not expose the required combination of open/closed ports to Nmap.

## Obstacle: Port State Instability

The two web ports were unreliable during enumeration and materially affected the workflow:

- `8090/tcp` and `8091/tcp` repeatedly flipped between **`open`** and **`filtered`** across successive scans, while `22/tcp` remained stable.
- At one point the **entire host became unreachable** (`Network is unreachable`) and even ICMP failed. A `traceroute` showed the VPN gateway (the last hop inside the tunnel) returning **`!N` (network unreachable)** for the `192.168.173.0/24` segment — i.e. a lab/VPN-side routing hiccup, not a target firewall blocking our probes.
- Connectivity returned a few minutes later with all three ports reachable again.

**Takeaway:** when ports flap or a host randomly disappears, distinguish an infrastructure/VPN problem from a target-side firewall before drawing conclusions. Re-check `ping` and `traceroute` to the tunnel gateway to localise the failure.

## Summary

- Host is a **Linux (Ubuntu)** machine.
- Only **three** TCP ports are open: **22 (SSH)**, **8090** and **8091** (unknown web services).
- SSH is a modern OpenSSH build — no obvious low-hanging fruit; the exposed **web services** are the interesting attack surface and are enumerated next.
